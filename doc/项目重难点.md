#### 数据分析Agent

ttagent 前期开发，做了工单目录匹配RAG搜索，后面负责做了沙箱接入，提供给agent用来执行skill管理安装和调用，代码执行，以及分用户分租户搭建沙箱内agent工作区workspace，支持上传文件，执行skill等操作。后续被同事封装成Java版本，提供RPC接口供学城Java后端调用

- **Vercel AI SDK 6** 构建生产级 Agent [文章](https://cloud.tencent.com/developer/article/2685429)
  - 基于 AI SDK 的工作范式：
    - 顺序处理（Sequential Processing）：连续调用streamText
    - 路由（Routing）
      - 场景：根据用户咨询类型（退款、技术支持、一般问题），分配给不同处理逻辑或不同大小的模型
      - 实现：先generateObject意图识别输出分类classification，再根据分类提示词调用streamText输出结果
    - 并行处理 (Parallel Processing)
      - 场景：代码审查（Code Review）。同时从“安全性”、“性能”和“可维护性”三个维度进行审查，最后汇总
      - 实现：使用Promise.all()请求多个不同提示词的 streamText，再汇总
    - 编排者-执行者 (Orchestrator-Worker)
      - 场景：实现一个新功能。编排者决定需要修改哪些文件，执行者分别去写每个文件的代码
      - 实现：generateObject拆分规划任务，streamText实现
    - ReAct 模式，评估-优化循环 (Evaluator-Optimizer)
      - 循环控制 TooLoopAgent：[文档](https://juejin.cn/post/7605769126271549486?from=search-suggest)
        - stopWhen：终止条件，可传入函数，比如：token 消耗超限终止循环
        - prepareStep：在循环的每一步发起大模型请求前运行，可以实现高度智能的动态行为
          - 根据 step > 3，切换到强模型；或者调整可用工具及调用规则
          - 上下文剪裁：messages.length > 20，滑动窗口裁剪只保留最近 10 条记录

#### 性能测试（Puppeteer、首屏性能优化）

**目标**：快搭表单设计部分存在性能上限，随着快搭稳定性建设的推进，需要进一步看清、关注表单搭建侧性能问题，保障快搭的稳定性，防止随着迭代进行性能降低。尽量避免会导致性能变差的改动在优化前就上线，影响线上的性能（FPS、FMP）导致潜在客诉风险
定义快搭场域下的测试场景
分场景给出性能指标定义
通过用例给出显现卡控的基准值

**运营机制SOP**：
快搭方案：每次测试后需预留一部分时间解决问题，防止指标超限时来不及处理，小版本测试方案见 快搭小版本发布性能测试方案，使用单独的工作机进行性能测试
学城方案：发布当天上午跑一次测试，遇到问题能解决就解决，不好解决就推迟上线
表格方案：每周三晚学城 st 合并发版本完成，使用合版本的分支进行性能测试，有问题第二天上午解决

  Runner 内置了已经定义好的测试 case，并抽象成了对应的 case 类，统一继承基类 BaseCase，表格场景下有：CanvasScrollCase-滚动性能、ModelPerformance-模型性能、GroupCase-分组功能等用例

  ```ts
  export abstract class BaseCase {
    private _result: any[] = [];
    init() {
      this._result = [];
    }
    // 负责用例执行
    async execute(page: Page, params: any = {}, repeatStep: number) {
      console.log('正在执行用例：', this.getKey());
      const ret = await this.onExecute(page, params, repeatStep);
      this._result.push(ret);
    }
    // 负责处理结果
    processResult(caseParams?: any, urlParams?: any) {
      return this.onProcessResult(this._result, caseParams, urlParams);
    }
    // 获取caseKey
    abstract getKey(): string;

    protected abstract onExecute(page: Page, params: any, repeatStep: number): Promise<any>;
    protected abstract onProcessResult(result: any[], caseParams?: any, urlParams?: any): any;
  }
  ```

- 指标说明：
  - 流畅维度（记录一段时间内的RAF列表）
    - 单帧最大渲染时长（maxRenderTimePerFrame）：列表里的最大值
    - 最小FPS（卡顿帧数量 worstFrameData）：统计连续大于 100 所消耗的时间对应的FPS，比如【20,200,100,20】，则卡顿帧平均耗时：（200+100) / 2 = 150ms，最终结果为（7FPS/2帧）
    - 平均FPS（averageFps）：列表的累加 / 列表的个数
    - 总卡顿帧数（jankFrameCount）：列表里 > 100 的个数
    - 总帧数（totalFrameCount）：列表里的个数
  - 响应维度：总时长、渲染时长（表格业务代码打点ZRender的绘制时间）
  - 内存维度：内存变化（memoryRange）：操作前，主动调用垃圾回收，获得JSHeapUsedSize。操作后，主动调用垃圾回收，获得JSHeapUsedSize

测试机制：

1. 测试环境：统一在外接显示器上进行(新款mac刷新率最高120Hz，会放大fps指标)，保持电脑只开启 vscode 及浏览器执行自动化测试用例，无其他资源占用
2. 测试时机：
   发布 release 后进行首次测试，st 合版后二次测试，与指标基准值比对决策是否卡控上线
   每次迭代除进行本迭代性能测试外，同时要对上一版本测试，保证两次迭代测试环境相对一致，使版本对比结果更准确
3. 输出报告：
   在当前目录下创建每个迭代的性能测试报告文档，报告格式见v1.9性能测试报告，在执行测试用例过程中如出现**阻塞性场景、输出报告中指标超出基准值时视为性能测试不通过 ❌**
   - ❌ 性能测试不通过：
     - 对该场景重新测试确认，同时研发介入判断性能问题严重程度，进一步定位原因，如不阻塞发布可正常发布，否则需要治理
     - 若因为业务迭代导致指标超出基准值上限，但业务侧仍需上线，需要周知@guan@Jerry Ma进行审批方可上线
     - 问题处理举例：
       阻塞的性能问题：引入的问题是黄金链路，需要修复或移除引入问题的需求
       边缘场景：为了保证整体稳定性，需要定位原因，评估影响并跟进
       常规性能问题：业务代码增加导致的性能问题（连续两个迭代异常后重新测试并更新基准值）
   - 性能测试通过：
     存在性能测试通过，但测试结果相比上一版本有波动场景，以下两种情况也需要配合需求开发者进一步定位、分析原因，防止性能渐进裂化到异常状态，无法及时发现和治理：
     - 连续两个版本及以上相比前一版本超过5%的波动
     - 相比上一迭代超过10%的波动
4. 指标基准值：有两种实施方案
   - 多次测试（10次）取性能最差的结果然后设置一个波动范围作为基准值（学城采用），需要分析并排除多次测试结果中明显异常的数据。
   - 多次测试取指标平均值，需要排除异常数据，基于该平均值设置一个波动范围作为基准值 **快搭采用**
     - **基准值选取原则**
       1、平均FPS，选取10次测试结果中最低的一次（这里不取平均值的原因：性能测试结果相对稳定的情况下，平均值和最低值的差距不大，取平均值的情况下则需要增大合理的误差范围），去除小数部分后再减1（误差值）作为基准值，例如58.62则选取57作为基准值
       2、单帧最大渲染时长，选取10次测试结果中最高的一次向上取整到10位整数，再加上50ms（误差值），例如测试得到195ms，则取250ms作为基准值
       3、根据单帧最大渲染时长计算最小FPS作为基准值，例如单帧最大渲染时长为250ms，则最小FPS的基准值应为1000ms/250ms = 4
       4、卡顿帧数，选取10次测试结果中最高的一次向上取整，取5的倍数，再加上5（误差值），例如测试得到卡顿帧数量为13，则取20作为基准值
5. 组件类型说明：
   以100组件为基准，200组件-500组件依次递增相同的组件类型，以看清性能变化趋势
   - 100组件：单行文本x4、多行文本x4、数字x4、金额x4、...
   - 200组件：单行文本x8、多行文本x8、数字x8、金额x8、...
6. 基准值定义及报告说明
   **快搭线下性能测试单一场景耗时较少，能够重复多次测试，这里基准值的定义暂定取平均值方案，来容错异常数据，提高指标的鲁棒性，按照上述两种基准值测试方案制定的基准值如下表：以下文中日程按钮组卡顿测试举例，两种基准值定义均能反映出性能问题**
   重点关注：单帧最大渲染时长、平均FPS，作为严格卡控指标，超出基准值分析原因，判断风险，决策能否上线
   辅助参考：卡顿帧数、总帧数、内存占用、首屏时间指标主要用于辅助判断，不作为上线评判卡控，超标时可根据情况分析
   测试用例执行次数：每个测试任务重复10次
7. 测试指标包含：静态指标和动态指标
   动态指标：组件选中、组件添加、组件复制、组件编辑、属性编辑、组件拖动、0-500组件添加内存变化、
   静态指标：和渲染器首屏、设计器首屏、渲染器表单解析时间、审批中心首屏 ![alt text](image-11.png)
8. 测试异常值处理：
   - 多次测试发现组件数量从100-500增加时，单帧最大渲染时长波动增大↑，偶现异常数据，但最大值和最小值差值总体保持在100ms内，平均FPS相对稳定，总体误差在5内
   - **方案**：针对单帧最大渲染时长异常数据，最终输出的单帧最大渲染时长结果采取移除最大值和最小值后取平均的方式输出，减少异常数据的影响，多次测试表明输出结果的稳定性得到提高
   - 测试首屏时间时发现，sso重定向时间会被统计到首屏时间内产生影响，以及环境问题、网络原因加载较慢也会导致首屏数据异常
   - **方案**：计算10次测试结果的平均值，超出平均值500ms的数据会被忽略，然后基于相对稳定的测试结果取平均值输出

#### 低代码引擎错误治理

**背景：**目前快搭表单设计侧，存在一些操作，会导致schema数据不合法，导致前台渲染时，存在一些异常。具体可以raptor中表单功能异常、表单hooks异常。raptor上无效告警较多，不利于排查问题，需要进行引擎问题修复处理这部分报错。
**目标：**1）raptor中表单异常告警清0：解决《引擎功能报错》一些存量问题，避免后续有新增问题时，无法感知。2）增加相应的能力（schema检测、规范等），避免已知问题在后续的开发中继续发生。3）治理完成后，增加 线上引擎功能报错 的监控，及时感知增量问题并治理。
**现状：**表单功能报错异常错误出现率较高，影响用户体验，平均周告警数量500+，影响用户数20+，主要包括以下场景：上报错误类型 proptype ：formula显示条件、datafilling数据填充

## 项目中遇到最大的困难是什么？

1.  动画场景使用 requestAnimationFrame（RAF）
    RAF原理：浏览器原⽣ API，专为浏览器设计。
    核⼼优势：与屏幕刷新率同步 60Hz/16.67ms，避免卡顿；RAF 在页面不可见时自动暂停，节省CPU，后台标签⻚⾃动暂停。可以将多次DOM操作合并到一帧内执行，在浏览器下一次重绘之前执行，避免布局抖动。解决了传统 `setTimeout/setInterval` 做动画时 “不同步、易卡顿、耗性能” 的问题

2.  为什么不用标准 EventSource，而是用fetch+post请求模拟 SSE ？
    - 核心原因：EventSource 只支持 GET，不能带 body
      - 发送一个消息需要携带 messages、会话 id 等字段，必须放在 body 里，因为消息内容可能很长（几千 token 的上下文），放 URL 里会超长，以及包含文件附件、结构化数据，URL 参数无法承载

4. SSE 相关（**复习文档76页**）
   - SSE 是⼀种服务器向客户端单向推送数据的技术，后端通过设置响应头 text/event-stream 格式持续发送数据块，前端逐步接收并渲染，形成打字机效果。

   ```
   后端设置：
   Content-Type: text/event-stream
   Cache-Control: no-cache
   Connection: keep-alive HTTP/1.1默认，让连接保持
   ```

   - 项⽬中如何使用？
     - 使⽤ fetch + ReadableStream ⽽⾮原⽣ EventSource（因为需要 POST 请求）；
     - 使⽤ eventsource-parser 库解析 SSE 格式；
     - ⽀持 [DONE] 标记结束流；
     - 配合 TypeWriter 实现打字机效果（⼀个实现打字机效果的⼯具类，⽤于在 AI 流式输出时，让⽂字逐字显示，模拟⼈类打字的视觉效果）
       - 原理：SSE 数据到达 → 加⼊队列 → 定时器逐字消费 → 界⾯逐字显示
       - 动态调整，队列⻓→快，队列短→慢；setTimeout 递归
       - 解耦⽹络速度与渲染速度，提供平滑体验
       - ⼀次性输出剩余内容，不拖沓
     - `ReadableStream`： Web Streams API 的核⼼接⼝，⽤于զၞ式̵分ࣘҁchunk҂ጱ⽅式᧛ݐ数ഝ，不必等
       全部数据加载完再处理，适合处理⼤⽂件、⽹络流式响应（如 SSE、视频流、AI 流式回答）。在浏览器中fetch() 返回的 response.body 就是⼀个 ReadableStream

   - SSE 如何处理断线重连？
     - 原⽣ EventSource 内置重连机制，连接中断时浏览器自动尝试重新连接，开发者无需手动处理
       - 支持历史事件 ID：可通过 last-event-id 请求头实现断点续传，避免数据丢失
     - fetch 实现需⼿动：利用 `Last-Event-ID` 请求头和消息中的`id`字段实现，断开时重新请求

   - 如何保证弱网环境下 SSE 的传输稳定性（**断网重连+断点续传**）？
     - 重连：循环到指定5次，间隔短到⻓（指数退避）
       - 最⼤重试次数 / 最⼤退避时间，计数器控制次数、setTimeout 控制间隔
       - 区分可重试错误（⽹络/5xx）和致命错误（401/403/4xx）
       - ⽹络恢复事件触发⽴即重连：window.addEventListener('online', () => sse.connect())
       - ⻚⾯ visibilitychange 时考虑暂停/恢复
     - **断点续传核心机制**： [文档](https://adg.csdn.net/695255255b9f5f31781b92f4.html)
       - 消息标识：服务端推送消息时在数据流中附加 `id/msgId` 字段，来唯一标识每条数据
       - 自动重连：连接意外中断时，浏览器会自动发起重连，并默认携带一个名为 `Last-Event-ID` 的 HTTP 请求头
       - 断点续传：服务端读取该请求头，即可知道客户端上一次成功接收的位置，从数据库或缓存中查询该 ID 之后的数据继续推送，字段不存在或为空则从头开始推送

         ```格式必须正确
         : 注释 # 可缺省
         id: 1001 # 消息ID
         event: 事件类型 # 可缺省
         data: 消息内容

         ```

       - 客户端必要保证：虽然浏览器会自动重连并发送 Last-Event-ID，但若遇到页面刷新或手动重连，原生的 `EventSource` 状态会丢失。为了实现绝对可靠的断点续传，前端建议做以下增强：监听更新：通过 `onmessage` 实时记录最新的 event.lastEventId 到 localStorage 或 SessionStorage 中。手动重建：在页面初始化时，读取本地存储的 ID，并将其拼接到 URL 中（如 /stream?lastEventId=xxx），服务端读取此参数即可作为起点
         > 客户端记住最后⼀次收到的 id（叫 lastEventId）
         > 重连时通过 Last-Event-ID 请求头告诉服务端
         > 服务端从这个 ID 之后的位置继续推送 → 实现断点续传
